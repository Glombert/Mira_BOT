# Брифинг для Kimi — клиенты для Mira

Это твоя главная инструкция. Читай целиком перед тем как писать код.

---

## 1. Кто такая Мира

Мира — персональный ИИ-агент на базе Claude/DeepSeek/Gemini. У неё есть характер: тёплая, любопытная, со своим мнением, не нейтральный инструмент. Она помогает владельцу (Андрей) и узкому кругу одобренных пользователей с задачами: разговор, файлы, Google Drive/Calendar/Sheets, напоминания.

Сейчас у Миры есть два интерфейса:
- **Telegram-бот** (рабочий)
- **Веб-интерфейс** (`web/app.py` — простой статический HTML + WS)

Твоя задача — построить **три новых клиента** к тому же бэкенду:
- **Web** (Next.js 14 App Router + TypeScript)
- **Desktop** (Electron, переиспользует Next.js-код через `electron-next` или статическую сборку)
- **Android** (React Native + TypeScript, отдельная кодовая база)

**Бэкенд трогать нельзя.** Он на VPS, описан в `docs/API.md`. Если тебе кажется что нужен новый эндпойнт — напиши Андрею, не лезь в `web/app.py` сам.

---

## 2. Цель и аудитория

- До 100 одобренных пользователей (родственники, друзья, бета-тестеры)
- Цель MVP: **полный паритет с Telegram-ботом** — всё что человек может сделать в Телеге, должен мочь и в новом клиенте
- Это не публичный продукт. Регистрации нет, только Telegram Login Widget. Аналитики не нужны, трекеров не нужно.

---

## 3. Стек (зафиксирован, не меняй)

| Платформа | Стек | Почему |
|---|---|---|
| Web | **Next.js 14** (App Router) + **TypeScript** + **TailwindCSS** | Стандартный, ты знаешь его хорошо |
| Desktop (Win/Linux) | **Electron** + та же Next.js-кодовая база (statically exported) | Один UI на 3 платформы |
| Android | **React Native** (0.74+) + **TypeScript** + **Expo Router** | Native UX, переиспользуем компонент-логику с веб |

**Общая внутренняя библиотека:** `packages/shared` с типами и API-клиентом — чтобы все три клиента дёргали один и тот же `MiraClient` класс. Описание ниже.

**Что нельзя использовать:**
- Redux/MobX/Zustand — для этого приложения достаточно React Context + `useReducer`. Не плоди state-менеджеры.
- Backend-as-a-Service (Supabase, Firebase) — backend уже есть, не нужен второй
- Markdown-парсеры с HTML-инъекцией. Только безопасные: `react-markdown` с `remark-gfm` + sanitize.
- Иконочные библиотеки с тысячами иконок. Бери `lucide-react` (минималистичный, дерево-трясётся).

## 4. Тон и характер UI

Мира — не Siri. У неё характер.

**Принципы копирайтинга:**
- **Тёплое, не корпоративное.** Не "Произошла ошибка обработки запроса. Повторите попытку." — а "Что-то пошло не так. Попробуй ещё раз."
- **На «ты», по-русски.** Английский язык в интерфейсе допустим только в технических вкраплениях (имена файлов, ID).
- **Короткое.** Если кнопке хватит одного слова — пусть будет одно слово.
- **Без жаргона.** "Чат" вместо "Conversation", "Файлы" вместо "Repository", "Напоминания" вместо "Scheduled Tasks".
- **Не извиняйся за саму себя.** UI не говорит "извини за неудобства". Если что-то сломалось — сообщи и предложи действие.

**Что Мира говорит в системных ситуациях** (это голос самой Миры, у тебя должно совпадать в UI):
- На превышение rate limit: «Эй, помедленнее — я ещё не успеваю отвечать.»
- На большой файл: «Файл слишком тяжёлый — я могу принимать до 20 МБ.»
- На блок: «Доступ закрыт.»
- На ошибку LLM: «Что-то пошло не так. Попробуй ещё раз.»

UI должен **отдельно** оформлять три типа сообщений:
- `message` от Миры — крупный, основной цвет, её аватар (звезда)
- `system` — компактный, приглушённый, в рамке, без аватара  
- `error` — тот же стиль что `system`, но с акцентным цветом

## 5. Дизайн-направление

Подробно — в `docs/design.md`. Кратко:

- **Тема:** только тёмная (light отложим, если попросит пользователь)
- **Палитра:** глубокий тёмный фон (почти чёрный с холодным оттенком), карточки чуть светлее, текст тёплый off-white. Акцент — **тёплый амбра/оранжевый**, как у переменной звезды Мира.
- **Типографика:** Inter (sans, кириллица обязательна), JetBrains Mono для технических вкраплений
- **Плотность:** свободная, не плотная. Это интимный инструмент для общения, не админ-панель
- **Анимации:** скупо. Появление сообщений fade+slide 200ms, индикатор "думает" — мягкая пульсация
- **Скругления:** 12-16px у карточек, 8px у кнопок, никаких острых углов

### `MiraClient` (в `packages/shared/src/api/`)

Один класс, который инкапсулирует всю работу с бэкендом. Он будет идентичен для веба и для RN — это главный профит общего пакета.

Минимальный API класса:

```typescript
class MiraClient {
  constructor(baseUrl: string, session?: string);
  
  // Auth
  async authenticate(telegramData: TelegramAuthData): Promise<AuthResult>;
  setSession(token: string): void;
  isAuthenticated(): boolean;
  
  // WS lifecycle
  connect(): Promise<void>;
  disconnect(): void;
  on<T extends ServerMessage['type']>(
    type: T,
    handler: (msg: Extract<ServerMessage, { type: T }>) => void
  ): () => void;
  
  // Sending
  sendMessage(text: string): void;
  sendCommand(cmd: string): void;
  
  // Files
  async uploadFile(file: File | Blob): Promise<UploadResult>;
  getDownloadUrl(dir: 'inbox' | 'output', filename: string): string;
  
  // Health
  async health(): Promise<HealthStatus>;
}
```

Типы сообщений (`ServerMessage`, `ClientMessage`) — из `docs/API.md` раздел 3. Сделай их discriminated unions по полю `type`.

### Конфигурация baseUrl

- Web/Desktop в production: `https://mira-bot.duckdns.org`
- Web/Desktop в dev: `http://localhost:8000`
- Android: то же что web (через переменную окружения `EXPO_PUBLIC_MIRA_URL`)

## 7. Что должно работать в MVP — полный паритет

**MVP = всё что есть в Telegram-боте.** Не упрощай и не вырезай.

### Чат
- Telegram Login Widget или OAuth (см. API.md раздел 1)
- Подключение к `/ws` после авторизации
- Отправка обычного сообщения → отображение `thinking` → отображение `message`
- Скролл, автоскролл к последнему, «прыгнуть вниз» если пользователь проскроллил вверх
- Рендер markdown в `message`-сообщениях (links, code blocks, lists) — sanitized
- Системные сообщения и ошибки — в отдельном стиле
- Очистка истории (команда `clear`)
- `whoami` — модалка с инфо о профиле

### Файлы
- Drag-and-drop в зону чата → POST `/upload`
- Показ прогресса загрузки (для крупных файлов)
- Команда `files` → список → ссылки на скачивание (`/files/{inbox|output}/{name}`)
- Обработка 413 (большой), 429 (rate limit), 401 (auth)

### Google интеграции (нужен статус `regular`/`owner`)
- Кнопка/команда «Привязать Google Drive» → открывает URL из `gdrive_auth_url`
- `gdrive_status`, `gdrive_list [folder]`, `gdrive_get <id>`
- Календарь: `gcal [N]`, `gcal_create <text>`
- Таблицы: `gsheet <id> [range]`, `gsheet_create [title]`

UI для Google-команд: отдельные кнопки/меню, не только командная строка. Пользователь не должен помнить точный синтаксис.

### Напоминания
- `remind <ISO> <text>` через UI: дата-пикер + поле текста + кнопка «Создать»
- `reminders` — список с возможностью отменить (кнопка → `remind_cancel <id>`)

### Состояние
- Reconnect при потере WS (с экспоненциальным backoff)
- `ping` каждые 30 секунд
- Сохранение последних N сообщений в локальном кэше (для мгновенного открытия; на сервере уже хранится)
- Индикатор статуса (онлайн / переподключение / оффлайн) в углу

### Что НЕ делать в MVP
- Не пытайся реализовать запрос истории за прошлые дни — такого эндпойнта нет. Клиент работает с текущей сессией; если её нет — начинает с приветствия.
- Не добавляй уведомления (push, system tray) — оставим на следующую версию.
- Не делай темизацию (light theme) — только dark.
- Не делай i18n — только русский.

- [ ] Авторизация через Telegram Login Widget работает

- [ ] Все 12 команд из API.md (3.3) запускаются из UI
- [ ] Drag-and-drop файлов работает, прогресс отображается
- [ ] Адаптивно от 360px до 1920px
- [ ] Lighthouse: Performance ≥ 90, Accessibility ≥ 95
- [ ] Нет console warnings/errors в production-сборке
- [ ] README c командами `npm install && npm run dev` и `npm run build`

**Desktop:**
- [ ] Бинарники для Windows (x64) и Linux (x64 .deb + AppImage)
- [ ] То же UI что в вебе
- [ ] Меню (Файл/Правка/Помощь) — нативное, не дублирует web-UI
- [ ] Авто-обновления **не настраиваем** (отложим)

- [ ] README с командой сборки

## 10. Workflow

1. Ты получаешь от меня этот брифинг + `docs/API.md` + `docs/design.md` + `docs/fixtures.json`
2. **Перед тем как писать код** — задай вопросы если что-то неясно. Не угадывай.
3. Делаешь по платформам в порядке: web → desktop → mobile. Каждая платформа — отдельный архив.
4. Отдаёшь `.zip`/`.tar.gz` с папкой `mira-clients/` внутри
5. Я (Claude) проверяю: компилится ли, соответствует ли API, безопасность, UX
6. Если ок — Андрей мерджит в свой репозиторий
7. Если правки — список замечаний → следующая итерация

## 11. Тестирование без живого бэкенда

Полагаться на VPS Андрея ты не должен. В `docs/fixtures.json` есть моки всех WS-сообщений и HTTP-ответов. Сделай **dev-режим** в `MiraClient`:
- Переменная `MIRA_DEV_MODE=mock` → клиент не лезет в сеть, отвечает из фикстур
- Это позволяет работать оффлайн и снимает нагрузку с VPS
